# ADR 0022: MariaDB SDK mutation contract

## Status

Accepted. Extends Phase 8 resource breadth.

## Context

MariaDB resembles the MySQL transport but does not have an identical creation
contract. The database user password is required, while the root password is
optional and may be generated by Dokploy. Password rotation remains a separate
operation that explicitly targets either the database user or root account.
Runtime detail responses expose both passwords and other fields that callers
must not retain.

## Decision

The public SDK exposes a strong `MariaDbId`, safe detail and search models, and
a bounded environment-scoped collection. Unknown response fields are tolerated
while passwords, environment variables, mounts, and other unowned runtime data
are absent from the safe models.

`CreateMariaDb` requires a zeroizing user password and offers an explicit
optional root-password builder. Both supplied passwords follow the pinned
Dokploy character contract and redact their debug output. Non-secret database
metadata updates remain separate from explicit user-or-root password changes.

The adapter uses pinned generated route and request metadata while keeping
narrow owned mutation bodies. Structured remote rejections remain available
to callers, and transport failures after dispatch remain outcome-unknown.
Environment search follows stable authoritative totals and rejects incomplete,
oversized, or contradictory pagination.

## Consequences

- Callers may let Dokploy generate a MariaDB root password without making that
  credential readable through the safe adapter.
- Supplied user and root passwords remain write-only and zeroize on drop.
- Password target selection is explicit and reviewable.
- Live contract capture never deploys the database. Dokploy `v0.30.6` therefore
  returns structured idle-database rejections for password changes; mock
  transport tests cover the successful wire contract.
